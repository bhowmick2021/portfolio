BigQuery cost governance

Cost drivers found in usage metadata, then fixed at the source.

PeriodAug 2025 – Jan 2026
RolePlatform owner, sole cost-governance operator
StackBigQuery, Dataplex, Cloud Storage, SQL, Python, FastAPI
AttributionDelivered at Radix Web Services

Problem

BigQuery spend was rising and the cost drivers were unclear across a large estate.

My contribution

  • Query and workload tuning, partitioning and clustering, lifecycle and metadata fixes.
  • Itemized, dated audit with slot-utilization analysis.
  • Leadership cost visibility: a dashboard showing where query cost concentrates, and Query Doctor, a pre-run cost estimator.

Decisions

  • Frame the result as BigQuery-specific, which is narrower but fully supported, rather than total cloud spend.
  • Itemize each fix with a status so savings stay traceable.
  • Give leaders a cost-concentration view and engineers a pre-run estimate.

Delivered change

  • Tuned queries and workloads.
  • Itemized fixes, for example Dataplex lineage tracking disabled and lifecycle rules on storage buckets.
  • BQ Most Expensive Queries dashboard (live) and Query Doctor.

Validation

A normalized before/after BigQuery cost comparison, with each audit line item marked done or pending.

Approved outcome

15–30% normalized BigQuery cost reduction (Aug 2025–Jan 2026). BigQuery only, not total GCP spend.

Not claimed

Not a total-cloud saving, and not a promise of the same percentage for any other team. The cost-governance method itself is not presented as AI-assisted; Query Doctor VNext is.

In my words, by audience

For Recruiters

I own BigQuery cost governance as the single operator across our cloud estate. Working with finance and engineering stakeholders I tuned queries and workloads, applied partitioning, clustering and lifecycle fixes, and gave leadership a clear view of where query cost concentrates. The result was a 15–30% normalized reduction in BigQuery cost between August 2025 and January 2026. It applies to BigQuery only and I describe it that way.

The Builder

I start from usage metadata to find where cost concentrates, then fix it at the source: query and workload tuning, partitioning and clustering, lifecycle rules and metadata clean-up. Each fix is itemized and dated so savings are traceable. I also built a dashboard for leadership and a tool that estimates a query's cost before it runs. Net result: 15–30% lower normalized BigQuery cost over about five months, BigQuery only.

The Consultant

At Radix, in my employer role, I reduced normalized BigQuery cost by 15–30% through query tuning, workload governance and itemized fixes. For your team I can start with a scoped, written review that ranks your main cost drivers and shows the expected benefit with assumptions based on your workload. I do not promise a fixed percentage.
